## 2. 단계별 로직

### 2-1. 실행 층 (`predict.ipynb`, `runner.py`)

- **시간 예산 방어.** 상한 2,400초를 넘기면 정량 0점이므로 전역 데드라인을 2,100초로 두고, 장당 예산을 `남은 시간 ÷ 남은 장수`로 매 장 다시 계산한다. 뒤로 갈수록 예산이 빠듯해지면 사다리가 스스로 얕은 단계에서 멈춘다. 순차 폴백 시에는 예산을 1배로 재계산한다(병렬 예산 ×4를 그대로 쓰면 초과).
- **재현성.** 워커당 스레드 1 고정(ONNX Runtime이 프로세스마다 코어를 전부 잡으면 서로 뺏어 느려지고, 결과도 흔들린다), 입력 순서 고정, 난수 없음.
- **격리.** 한 장이 예외를 내면 그 행만 NONE으로 채우고 나머지는 살린다.

### 2-2. OCR 판독 사다리 (`ocr_ladder.py`, V6)

설계의 뼈대는 **"모든 연산을 모든 이미지에 하지 않는다"**이다. 1차 판독에서 답이 나오면 즉시 끝내고, 실패한 장에만 다음 수단을 순차 투입한다.

| 단계 | 처리 | 투입 조건 | 근거 |
|---|---|---|---|
| EXIF | 촬영 방향 메타데이터로 회전 복원 | 전 이미지 | 폰 사진은 픽셀이 눕혀진 채 저장되는 경우가 많다 |
| 0 | 800 → 1280 → 1920px LANCZOS 축소 후 판독. 원본의 2배를 넘는 확대는 금지 | 전 이미지. 판별기가 **완전한 날짜**를 내면 즉시 종료 | 배율별 판독 성패가 이미지마다 무작위(000522는 1920에서만, 001361은 800·1280에서만). 2배 초과 확대는 판독 악화 + 시간 44.7→32.5분 |
| 0.5 | CLAHE(clip 2.0, 8×8) 1280px | 0단계 실패 시 | 난반사·국부 음영 완화. 300장 실측 단독 기여 0, 비용 0.1초 — 유지하되 제거 가능 |
| 1 | 회전 270/90/180/15/345° 1280px | 실패 시 | 실패 장 구제율 1위(67%)라 앞에 배치. ±15°는 매대 촬영분 기울기 대응 |
| 1.5 | 적응형 이진화(가우시안 21, C=10, 반전) + 팽창 2×2 1280px | 실패 시 | 도트 매트릭스 점선을 실선으로 잇는다. 300장에서 이 단계가 살린 장 2건 |
| **부분 날짜 종료** | 연·월·일 중 **2칸 이상** 채워졌으면 여기서 멈춤 | | 정답이 애초에 `2022-05-NONE`처럼 부분 날짜인 장은 완전한 날짜가 나올 수 없어 항상 사다리 끝(17~20초)까지 내려갔다. 300장 중 사다리를 탄 41장이 전체 시간의 66%를 썼고 그중 12장이 이 경우. 실측 시간 −13%, 정확도 +1 |
| 2 | 0단계 상자 좌표를 원본 해상도로 되돌려 크롭 재인식(숫자 포함 상자 최대 6개, 작으면 480px로 확대) | 실패 시 | 「검출은 작게, 인식은 원본으로」. 4,032px 원본을 800px로 줄이면 각인이 1/5로 뭉개진다 |
| 3 | 전체 1920px | 실패 시. **0단계에서 scale1920을 이미 읽었으면 건너뜀** | 중복 실행 제거(장당 2.5초) |
| 4 | 자동 대비 스트레치(cutoff 2%) + 언샤프 1600px | 최후 수단 | 구제율 15%. 여기까지 온 장은 대부분 판독 불가 사진 |

**조기 종료 판정(`_hit`)이 판별기를 호출하는 이유.** 날짜꼴 정규식만으로 멈추면 800px에서 `2021.10.15`처럼 오독된 숫자만 보여도 멈춰버린다. 판별기가 연·월·일을 모두 채운 **완전한 날짜**를 냈을 때만 멈추면 오독 상태에서 다음 배율·회전을 더 읽어 볼 기회가 생긴다. 실측: 정규식 판정으로 바꾸면 −16건(V1). 이 판정이 곧 다중 배율 병합의 역할을 하므로 3배율을 항상 합치는 방식은 오히려 시간 +48%, 정확도 −9(V2).

### 2-3. 날짜 판별기 (`date_resolver.py`, R4)

**설계 원칙: 읽기와 고르기는 다른 문제다.** OCR 신뢰도 0.99로 읽힌 숫자가 제조일자일 수 있다. 그래서 판별기는 OCR 신뢰도를 쓰지 않고, 날짜 유효성 → 완성도 → 문맥 → 날짜 간 관계 순으로 판정한다.

**⓪ R4 형태 정규화** — 판별 전에 OCR 원문의 정형화된 깨짐을 되돌린다 (이미지 ID·브랜드명 없음).

| 규칙 | 실측 예 | 300장 득 |
|---|---|---|
| `YYYYMM.DDx` (첫 구분자 탈락 + 꼬리 숫자) → `YYYY.MM.DD` | `202807.257` → 2028-07-25 | +2 |
| `DD/MMYYYY` (둘째 구분자 탈락) → `DD/MM/YYYY` | `EXP:26/062026` | +1 |
| `YYYY.MM.DDD`+영문 (일 자리 3자리) → 앞 두 자리 | `2021.09.030A5` → 2021-09-03 | +1 |
| `YYYY.MMXDD` (일 앞 X 잡음) | `2023.01X13` | +1 |
| `MM.YYYY` / `MM/YYYY` / `MON YYYY` (연·월만) → `YYYY.MM` | `EXP:01.2022`, `12/2021`, `SEP 2022` → day NONE | +7 |

앞에 `DD.`가 붙은 `01/11/2021`, `29.Jan2024`에는 켜지지 않도록 lookbehind로 막았다. 검증: 300장 +12/−0, 개발150 +2/−0, 봉인200 +1/−0.

**① 정규화·노이즈 제거.** NFKC → 대문자 → 구분자 통일(`, ; : · ' *` → `.`, `_ — ~` → `-`, `\ |` → `/`). 3단 콜론(`26:09:16`)은 시각이 아니라 날짜로 선변환. 시각(`HH:MM`), 전화번호, 13자리 바코드, 천 단위 가격, `kcal/mg/ml/kg`는 후보에서 제거.

**② 후보 생성 (전부 OCR 상자 단위).**
- 월 이름: 정식 12개 + 글자 혼동 규칙(`J→I L 1 T`, `A→4 R`, `E→F B 8`, `O→0 Q D C`, `S→5` …)으로 자동 생성한 약 200개 변형. 실제 영단어가 되는 것(WAR·MAP·JAM…)은 제외. 정식 이름은 150점, 변형은 60점(약한 증거). 좌우 숫자를 일·연으로 짝짓되, 그 상자에 없으면 좌우 한 상자까지만 확장하고 −30.
- 숫자: `A.B.C` 3묶음, 8자리 연속(`YYYYMMDD` 또는 `DDMMYYYY` 둘 다 후보), `YYYYMM.DD`(첫 구분자 탈락), `YYYY.MM`(일 없음), 6자리 연속(예비후보 −25, 확실한 날짜가 있으면 폐기), `MM.DD`(연도 없음).
- 인접 박스 결합: `EXP:` `2022` `08` `13`처럼 쪼개진 숫자 토큰이 3개 이상 연달아 나오면 3칸씩 밀며 후보 생성. 오탐 0을 지키기 위해 완전한 날짜일 때만 채택, 구분자 날짜보다 −18.

**③ 형식 결정론 (`_split3`).** 숫자 3묶음의 해석은 언제나 하나로 정해진다.

| 조건 | 해석 |
|---|---|
| 앞 칸 4자리 | YYYY.MM.DD, 가운데 ≥13이면 YYYY.DD.MM |
| 뒤 칸 4자리 | DD/MM/YYYY 기본, 둘째 칸 ≥13이면 MM/DD/YYYY (실측 DD/MM 41 : MM/DD 4) |
| 전부 2자리, 앞 칸이 해석창 `[올해−7, 올해+1]` 안 | YY.MM.DD (한국 관행) |
| 전부 2자리, 뒤 칸만 창 안 | DD.MM.YY |
| 연도 후보 없음 | 날짜 아님 |

2자리 연도 해석창은 하한 19 고정, 상한 = 시스템 시계 + 1. 상한의 역할은 "아직 오지 않은 연도 배제"라 오늘에 의존하고, 하한의 역할은 "일자(1~31)를 연도로 오독하지 않기"라 달력과 무관하다. 하한을 시계에 묶으면 2029년 실행 시 83.5% → 76.8%로 무너진다(시뮬레이션). 4자리 연도의 유효 범위(2015 ~ 올해+8)는 이와 별개라 `2028.06.23`은 정상 처리된다.

**④ 칸 단위 검증.** 연도가 범위 밖이면 연도만, 월이 1~12 밖이면 월만, 존재하지 않는 날(2026-02-30)이면 일만 버린다. 통째로 버리지 않는다.

**⑤ 점수.** 완성도(3칸 +20 / 2칸 +8) + 소비기한 키워드(`소비기한·유통기한·까지·BEST BEFORE·USE BY·EXP·BBE`) 인접 +30 − 제조일자 키워드(`제조일자·MFG·MFD·PACKED`) 인접 35 − 절단 10 − 6자리 예비후보 25. 키워드 문맥은 반드시 **그 날짜가 찍힌 상자** 안에서만 본다. 전체 문자열 ±40자로 보면 제조일자와 소비기한이 서로의 문맥을 침범한다(실측 버그).

**⑥ 정렬.** 점수 → 채워진 칸 수 → **동점일 때만** 더 늦은 날짜. "늦은 날짜 = 소비기한"은 두 후보가 모두 제대로 읽힌 진짜 날짜일 때만 성립하므로 마지막 순위에 둔다.

**⑦ 래퍼 CASE.** 코어가 NONE이면 특수 포맷 구제(반복 연도 `2626.08.13`, 붙은 로트, `YYYY.MMDD`, 공백 구분, 붙은 월 이름) 후 재시도(CASE 1). 미국 바코드(UPC 접두 0~139)·`NET WT`면 DD.MM.YY → MM.DD 교체(CASE 2). 유럽 키워드면 DD.MM.YY 강제(CASE 4). `EXP`와 `PROD`가 공존하면 EXP 쪽 채택(CASE 5). 도트 오독 `6→0`, `W→.`(CASE 6). 부분 날짜는 `2022-01-NONE` 형식으로 결합(CASE 7).

**⑧ votes.** 같은 날짜가 나온 판독 경로 수를 출력에 남긴다. 가점으로 쓰면 손해(제조일자도 모든 배율에서 똑같이 잘 읽히므로)라 판정에는 쓰지 않는다. 예선 시점에는 운영 단계의 자동/사람 검수 분기 근거로 썼으나(1경로 75.6% / 2경로 93.9% / 3경로+ 98.8%), 최종 모델은 조기 종료로 대부분의 이미지가 경로 1개만 거쳐(미사용 300장 중 240장) 이 값이 신뢰도를 나타내지 못한다. 운영 단계의 분기 기준은 판독이 종료된 사다리 단계로 대체하였다(미사용 300장: 0단계 종료 270장 정확도 92.2%, 1단계 이상 30장 16.7%).

## 4. 왜 이 로직이 합리적인가

**(1) 손실을 분해하고 그 분해에 따라 처방한다.** 정확도 손실은 "OCR이 못 읽음"(검출 손실)과 "읽었는데 잘못 고름"(판별 손실)으로 나뉘고 해결 수단이 완전히 다르다. 정답 날짜가 OCR 출력 어딘가에 들어 있는 비율(도달 상한)을 별도로 재면, 상한 − 정확도 = 판별 손실, 100 − 상한 = 검출 손실이다. 이 도구가 없었으면 봉인셋 12%p 격차를 "규칙 과적합"으로 오진했을 것이다(실제로는 1.9%p만 과적합, 8.5%p는 검출 손실). 본선 스위프도 같은 도구로 "임계값을 낮춰도 상한이 1%p밖에 안 오르고 그마저 판별기가 못 바꾼다"를 보여 검출 파라미터를 기각했다.

**(2) 읽기와 고르기를 분리한다.** OCR 신뢰도는 "읽기 쉬운 정도"를 잴 뿐 "이것이 소비기한인가"를 재지 못한다. 제조일자는 소비기한만큼 또렷하게 인쇄된다. 그래서 판별기는 신뢰도 대신 날짜 문법(형식·유효성)과 문맥(키워드)으로 판정하고, 다중 경로 일치도는 판정이 아닌 신뢰도 진단에만 쓴다. Seker & Ahn(2022)이 소비기한 인식을 "영역 검출 → 인식 → 해석"의 독립 단계로 분리한 것과 같은 구조다.

**(3) 조기 종료는 정확도 장치이자 속도 장치다.** 판별기가 완전한 날짜를 낼 때만 멈추면, 800px에서 오독된 숫자만 보인 장은 자동으로 1280·1920·회전으로 넘어간다. 즉 "여러 배율을 합친다"는 목표를 상시 병합 없이 실패한 장에만 비용을 들여 달성한다. 86%의 이미지는 1.27초에 끝나고, 나머지 14%가 나머지 시간을 쓴다. 부분 날짜 종료는 이 원리의 빈틈(완전한 날짜가 나올 수 없는 장)을 메운 것이다.

**(4) 형식 판별은 결정론이어야 한다.** 점수제(v2~v3)는 규칙 충돌은 없앴지만 "왜 이 답인가"를 설명할 수 없었다. 결정론(v4)은 숫자 묶음 하나에 해석 하나를 대응시키므로 오답을 규칙 단위로 추적할 수 있고, 심사 기준의 "근거 명확성"에 직접 답한다. 해석창 `[올해−7, 올해+1]`의 폭은 650장 실측(2자리 연도 관측 범위 2019~2027)으로 정했고, 두 경계 모두 실행 시점에서 유도한다. 하한을 상수로 두면 실행 연도가 지날수록 창이 한쪽으로만 넓어져 일자와 연도의 구분력이 떨어지기 때문이다. 폭은 환경변수 `ITDA_YY_BACK`, `ITDA_YY_FWD`로 운영 환경에 맞게 조정할 수 있다(2026-09-27 변경, 300장 재채점 264/300 동일).

**(5) 오탐보다 NONE이 낫다.** 부분점수 체계에서 없는 날짜를 지어내면 3칸이 전부 날아가고, 실사용에서는 경과 상품이 "정상"으로 통과하는 가장 위험한 오류가 된다. 그래서 칸 단위로 버리고, 결합 후보는 완전할 때만 채택하며, 6자리 예비후보는 확실한 날짜가 있으면 폐기한다. 650장 오탐 2건, 300장 오탐 3건이 이 원칙의 결과다. "무조건 늦은 날짜"를 끈 것도 같은 맥락이다 — 그 규칙은 오독 변종을 진짜 날짜로 승격시켜 오탐을 만든다.

**(6) 직관이 아니라 실측으로 채택한다.** 투표 가점, 늦은 날짜 무조건 우선, 잘린 연도 복원, 검출 임계값 하향, 정규식 조기 종료, 3배율 상시 병합 — 전부 합리적으로 들렸고 전부 실측에서 손해였다. 반대로 부분 날짜 종료와 R4 정규화는 오답 목록에서 형태를 뽑아 규칙화한 뒤 규칙을 만들 때 보지 않은 셋(개발150·봉인200)에서 손실 0을 확인하고 채택했다. 규칙에 이미지 ID·브랜드명은 넣지 않는다.

## 6. 유의점과 남은 과제

- **플랫폼 차이.** 같은 코드를 Mac(arm64, onnxruntime 1.23)에서 돌리면 x86 컨테이너 대비 22건 얻고 21건 잃는 식으로 숫자 오독이 갈린다. 채점 환경은 x86 Ubuntu이므로 x86 수치를 대표값으로 쓰고, 두 환경을 섞어 비교하지 않는다.
- **부분 날짜 `final_date` 포맷.** 현재 코드는 `2022-01-NONE`으로 결합해 출력한다. 채점기가 이를 정답으로 보는지, `NONE`을 기대하는지 운영진 확인이 필요하다.
- **`requirements.txt`** 는 `>=`가 아니라 `==`로 고정해야 검수 재현성이 보장된다.
- **남은 오답 36건(300장)**: 약 30건은 OCR이 아예 못 읽는 장(캔 뚜껑 음각·병 각인·제조일+시각만 읽힘), 약 6건은 진짜 애매한 표기(`17.03.22`의 2017 vs 2022, `05.21L0952`의 MM.YY+로트). 후처리로 짜낼 여지는 거의 없고 남은 것은 촬영·인쇄 자체의 한계다.
- **하드코딩 정리.** CASE 1의 `9EP/JLL` 수동 등록, `EU_KEYWORDS`·`KR_INDICATORS`의 브랜드명은 심사에서 특정 데이터 암기로 보일 수 있다. 월 이름은 CONFUSE 자동 생성으로 대체 가능하고, 국가 판별은 바코드 접두·언어 키워드로 한정하는 편이 안전하다.
